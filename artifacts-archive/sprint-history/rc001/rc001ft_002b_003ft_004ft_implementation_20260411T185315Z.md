## RC-001ft — SEC Filing Financial Coverage & Underwriting Exemption

### Problem
Public companies (S-1, 10-K, 10-Q filers) were being penalized on financial coverage and underwriting readiness for not having an XLSX model. SEC filings contain audited financial statements that are structurally equivalent to or higher quality than an unaudited XLSX model.

### Solution

**`packages/core/src/models/financial-coverage-profile.ts`**
- Added `doc_type_hints?: string[] | null` parameter to `inferFinancialCoverageProfileV1`
- If `sec_filing_s1`, `sec_filing_10k`, or `sec_filing_10q` hint present:
  - Removes the `deck` source entry, replaces with `{ kind: 'other', notes: 'sec_filing_authoritative' }`  
  - Floors `confidence` to `medium` (never `low` for SEC filers)
  - Adds `sec_filing_present` to notes array

**`packages/core/src/models/financial-breakdown-v1.ts`**
- Added `sec_filing_no_xlsx` to `UnderwritingReadinessGap` type union
- Modified `_buildReadiness`: if `cov.notes.includes('sec_filing_present')` and no XLSX, awards +20 pts and uses `sec_filing_no_xlsx` gap instead of `deck_only`

**`packages/core/src/reports/compiler-simple.ts`**
- In `compileDIOToReportWithPromotedFacts`: extracts `_docTypeHints` once from DIO claims text, passes to both `inferFundingStageModelV1` and `inferFinancialCoverageProfileV1`
- In `compileDIOToReport`: passes `_docTypeHintsForFunding` to `inferFinancialCoverageProfileV1`

## RC-002b — Going Concern → Report Red Flags

### Problem
Going concern language in SEC filings (Form 10-K, annual reports) was not surfacing as a high-severity red flag in the compiled report. The DIO `phase1.claims` only contains brief summary texts ("Risk signals: Competition, Retention risk…") — the full going concern language is stored in `document_page_understanding` page-level text rows.

### Root Cause
The original RC-002b scanner in `compileDIOToReport` checked only `dio.phase1.claims[*].{text, evidence[*].snippet}`. The full going concern text is in `document_page_understanding.payload->>'page_text'` which is not part of the DIO object.

### Solution

**Two-layer scan:**

1. **`compileDIOToReport`** (in `packages/core/src/reports/compiler-simple.ts`): Scans DIO claims/evidence snippets for going concern regex. Covers cases where the DIO captures the language directly.

2. **`compileDIOToReportWithPromotedFacts`** (same file): Accepts new `pageTexts?: string[] | null` option. After calling `compileDIOToReport(dio)` to get the base, runs a second going concern scan over `pageTexts`. If triggered (and not already in base redFlags), pushes a `high` severity flag and merges into the returned report's `redFlags`.

**`apps/api/src/routes/financial-facts.ts`**
- Added `getGoingConcernPageTexts(pool, dealId)` helper function
- Queries `document_page_understanding` for rows where `payload->>'page_text' ~* '<going concern pattern>'`
- Uses POSIX `[[:space:]]` character class (not `\s`) for PostgreSQL regex compatibility
- Never throws — returns `[]` on error

**`apps/api/src/routes/reports.ts`**
- Imported `getGoingConcernPageTexts`
- Both `compileDIOToReportWithPromotedFacts` call sites now query and pass `pageTexts`

### Regex pattern (PostgreSQL)
```
ability[[:space:]]+to[[:space:]]+continue[[:space:]]+as[[:space:]]+a[[:space:]]+going[[:space:]]+concern
| substantial[[:space:]]+doubt.*going[[:space:]]+concern
| going[[:space:]]+concern.*substantial[[:space:]]+doubt
```

## RC-003ft — False Revenue Guard Audit

### Problem
Concern that KPI tile marketing language (e.g., "$1B market size") could pollute financial coverage profiles as false revenue signals.

### Audit Result
**No code change required.** The existing guards in `inferFinancialCoverageProfileV1` already:
- Do not populate `historical_revenue_present` from deck language
- Require structured facts with `fact_type: 'revenue_v1'` from XLSX/PDF extraction
- The `FieldAuthorityGuard` in `compileDIOToReportWithPromotedFacts` already blocks promoted facts that don't originate from authoritative document sources for revenue fields

The market-sizing revenue pattern guard was confirmed correct by code inspection.

## RC-004ft — IPO/Public Company Stage Propagation

### Problem
`ipo` and `public_company` were valid output values from `inferFundingStageModelV1` but were rejected by the stage type guard in `conviction-v1.ts`, which only accepted `pre_seed | seed | series_a | growth | unknown`. This caused the conviction layer to treat ipo/public_company deals as `unknown` stage.

### Solution

**`packages/core/src/reports/conviction-calibration.ts`**
- Extended `ConvictionFundingStage` type: added `| 'ipo' | 'public_company'`

**`packages/core/src/reports/conviction-v1.ts`**
- Extended the stage guard in `computeConvictionV1` to pass `ipo` and `public_company` through
- Both values fall into the `"strict"` bucket in `stageBucket()` (same as `growth`) — correct behavior for late-stage/public company KPI expectations

### Live Validation (NerdWallet S-1)
```
funding_stage_v1.stage: 'ipo'  ✅
```
